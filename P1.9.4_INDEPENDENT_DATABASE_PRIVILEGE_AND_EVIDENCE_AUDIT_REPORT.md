## 1. Executive Summary & Verdict Matrix

In Phase P1.9.3, relational proof was introduced to stop ordinary ingestion feeds from forging source strings (`'NSE_CORPORATE_ACTION'`, `'PRIMARY_EXCHANGE'`). In this P1.9.4 audit, an independent security investigation of the deployed database privileges, catalog objects, and evidence authorization boundaries was conducted.

The audit revealed three critical architectural vulnerabilities:
1. **Absence of Role Separation:** The application was running as PostgreSQL superuser `halal_user`. A compromised application connection or writer could disable triggers (`ALTER TABLE ohlcv_daily DISABLE TRIGGER ALL;`), alter trigger functions, or modify table definitions.
2. **Manufactured Relational Proof:** There were no guard triggers on `corporate_action_events` or `corporate_action_adjustment_factors`. An application writer could directly insert a fabricated event claiming `verification_status = 'VERIFIED_EXCHANGE_PRIMARY'` and a matching factor with `is_verified = true`, thereby manufacturing the relational proof required to un-quarantine historical bars.
3. **Overly Permissive `SECURITY DEFINER` Procedure:** `ca.apply_verified_corporate_action()` had `GRANT EXECUTE ... TO PUBLIC`, was owned by login superuser `halal_user`, and did not verify the cryptographic SHA256 checksum or authenticity of the underlying source artifact.

**Remediation Deployed:** **Migration 20** ([`20-p194-database-privilege-and-evidence-authorization.sql`](file:///Users/fayas/Downloads/ICO-Application/analysis%20application/backend/migrations/20-p194-database-privilege-and-evidence-authorization.sql)) established strict role separation (`ca_security_admin` non-login owner, `halal_app_user` least-privilege role), revoked `PUBLIC` execution, introduced `trg_ca_event_verification_guard` and hardened `ca_factor_ingest_guard` to require authenticated exchange artifacts with valid 64-char SHA256 checksums, and added full chain-of-custody verification to `ca.apply_verified_corporate_action()`.

## 2. Forensic Analysis of Findings & Privilege Remediation

### Finding P1.9.4-F1 (Severity: CRITICAL) — Relational Proof Manufacturing Bypass
- **Description:** While P1.9.3 prevented source strings from bypassing quarantine, any database client could insert an unverified event with `verification_status = 'VERIFIED_EXCHANGE_PRIMARY'` and an adjustment factor with `is_verified = TRUE`, manufacturing the relational proof expected by `fn_ohlcv_daily_quarantine_guard()`.
- **Pre-Fix Reproduction:**
  ```sql
  BEGIN;
  INSERT INTO corporate_action_events (event_id, symbol_id, symbol, action_type, source_subject, ex_date, currency, verification_status, coverage_status)
  VALUES ('TEST:FORGED:EVENT', 10, 'HCLTECH', 'CASH_DIVIDEND', 'Forged Evidence', '2026-10-14', 'INR', 'VERIFIED_EXCHANGE_PRIMARY', 'HARVESTED_EXCHANGE_PRIMARY');
  
  INSERT INTO corporate_action_adjustment_factors (symbol_id, action_type, ex_date, effective_date, adjustment_factor, nominal_price_factor, total_return_factor, volume_adjustment_factor, source_reference, is_verified, verification_status, factor_category, price_factor_applicable, dispute_status, event_id)
  VALUES (10, 'CASH_DIVIDEND', '2026-10-14', '2026-10-14', 0.90, 1.0, 0.90, 1.0, 'Forged Evidence', true, 'VERIFIED_EXCHANGE_PRIMARY', 'TOTAL_RETURN_FACTOR', true, 'UNDISPUTED', 'TEST:FORGED:EVENT');
  
  UPDATE ohlcv_daily SET adjusted_close = ROUND(close * 0.90, 4), source = 'NSE_CORPORATE_ACTION' WHERE symbol_id = 10 AND timestamp::date = '2026-10-06';
  -- Result: UPDATE 1 (Quarantined NULL was un-quarantined!)
  ROLLBACK;
  ```
- **Post-Fix Verification:** Intercepted by `trg_ca_event_verification_guard`:
  `ERROR: Event verification rejected: VERIFIED_EXCHANGE_PRIMARY requires source_artifact_id to be populated (event_id=TEST:FORGED:EVENT)`.

### Finding P1.9.4-F2 (Severity: CRITICAL) — Superuser Application Connection
- **Description:** The application stack (`backend`, `worker`, `quant`) connected as `halal_user` (`rolsuper = t`). PostgreSQL superusers bypass table permissions, can disable all triggers, and can alter trigger definitions.
- **Post-Fix Resolution:** Created non-superuser application role `halal_app_user` (`NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`). Granted least-privilege `SELECT, INSERT, UPDATE` on `ohlcv_daily` and `SELECT` on reference tables. When connecting as `halal_app_user`, executing `ALTER TABLE ohlcv_daily DISABLE TRIGGER ALL;` yields `ERROR: must be owner of table ohlcv_daily`.

### Finding P1.9.4-F3 (Severity: HIGH) — `SECURITY DEFINER` Granted to `PUBLIC`
- **Description:** Migration 19 granted `EXECUTE ON FUNCTION ca.apply_verified_corporate_action TO PUBLIC`. Any connected user could execute the procedure. In addition, the procedure was owned by superuser `halal_user`.
- **Post-Fix Resolution:**
  1. Revoked `EXECUTE` from `PUBLIC` and revoked `USAGE` on schema `ca` from `PUBLIC`.
  2. Transferred procedure ownership to non-login system role `ca_security_admin`.
  3. Granted `EXECUTE` only to explicit authorized roles (`halal_user`, `halal_app_user`).
  4. Added full cryptographic chain of custody: requires join to `corporate_action_source_artifacts` with valid 64-char SHA256 checksum and primary exchange authority (`NSE_INDIA` / `BSE_INDIA`).
