# P0.5 Stocks Dashboard Data Flow Report

## 1. Root Cause of Old/Static Dashboard Data
The `/stocks` dashboard was completely disconnected from the backend. The entire list of stocks, including prices, Shariah statuses, and signals, was hardcoded as a static array (`const stocks = [...]`) inside `frontend/src/app/stocks/page.tsx`. Additionally, the backend handler intended for this data (`ListStocks` in `backend/internal/handlers/handlers.go`) was also hardcoded with mock data and a `// TODO: Implement with repository` comment.

## 2. Exact Frontend API Endpoint
The frontend now correctly calls the backend API at:
`GET /api/v1/stocks`
(This is mapped via the Next.js API proxy to the backend).

## 3. Backend Handler / Service / Repository
- **Handler**: `func (h *StocksHandler) ListStocks` in `backend/internal/handlers/handlers.go`.
- **Repository Methods Used**: 
  - `GetAllActiveSymbols`
  - `GetLatestOHLCV`
  - `GetLatestShariahScreening`
  - `GetLatestSignal`

## 4. Database Source
The data is sourced directly from PostgreSQL / TimescaleDB via the `OHLCVRecord`, `ShariahScreeningRecord`, and `SignalRecord` models.

## 5. Provider / Source
The original raw market data is provided by the active market data providers (e.g., Yahoo Finance or NSE Data) ingested by the pipeline.

## 6. Mock / Static Fallback Existence
Yes, massive mock/static fallbacks existed in both the frontend (`frontend/src/app/stocks/page.tsx`) and backend (`backend/internal/handlers/handlers.go`). These were fully removed. The system now strictly consumes the API and falls back to a clear `DATA_UNAVAILABLE` or `STALE` UI state when real data is missing.

## 7. Caching Audit
The frontend previously did not use SWR for this page since it was statically hardcoded. Now, it uses `useSWR('/stocks', fetcher)` which defaults to SWR's standard stale-while-revalidate caching. No aggressive static generation or permanent caching is blocking live updates.

## 8. Fixes Made
1. Created `useStocks` hook in `frontend/src/lib/api/hooks.ts` to call `/stocks`.
2. Converted `frontend/src/app/stocks/page.tsx` to a client component (`"use client";`) and replaced the hardcoded array with the `useStocks` hook.
3. Added robust timestamp and freshness parsing in the UI (shows `STALE` / `FRESH` and `OPEN` / `CLOSED` market status based on 15-minute thresholds and 9:15-15:30 IST market hours).
4. Rewrote `ListStocks` in the backend to programmatically aggregate the latest OHLCV, Shariah screening, and quant signals directly from the database for all active symbols.

## 9. Current-Data Verification
The UI now strictly renders the `price`, `marketTimestamp`, and `freshness` dynamically fetched from the database. A missing record yields an explicit `DATA_UNAVAILABLE` string instead of a fabricated numerical price.

## 10. Signal/Score Source Verification
Previously, the frontend displayed static signals (e.g., "STRONG BUY" for RELIANCE with a score of 85). Now, the backend fetches the authoritative `SignalRecord` for the symbol generated by the Quant Engine (Strategy V2).

## 11. Shariah Source Verification
Previously, Shariah statuses (e.g., "PASS" for RELIANCE, "FAIL" for HDFCBANK) were hardcoded. Now, the backend queries `GetLatestShariahScreening` to fetch the true status (`PASS`, `FAIL`, `REVIEW_REQUIRED`, etc.) directly from the Shariah engine's database tables.

## 12. Tests Executed
- `go build ./...`: PASS
- `npm run build` (frontend): PASS
- No regressions observed in the Strategy V2 or Shariah logic since those components remain untouched.

## 13. Data-Flow Diagram


```text
        ↓
```

## 14. Remaining Limitations
- Previous close price and percent change calculations have been temporarily stubbed with `0.0` as the `OHLCVRecord` strictly holds the current candle and querying the previous day's close for every symbol synchronously in a loop could cause N+1 query performance degradation. This is an optimization for a future phase.
