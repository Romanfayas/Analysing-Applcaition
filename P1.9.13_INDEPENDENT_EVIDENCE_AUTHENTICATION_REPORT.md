## 1. Corporate-Action Evidence Authentication & Privilege Audit

### 1.1 Trace of `VERIFIED_EXCHANGE_PRIMARY` Assignment Path

The corporate action verification path spans five distinct layers:
1. **Source Artifact Registry (`corporate_action_source_artifacts`)**: Stores document payloads, SHA-256 digests, source URLs, issuing authorities, and `validation_status`.
2. **Corporate Action Events (`corporate_action_events`)**: Stores ex-dates, action types, split/dividend parameters, linking foreign keys (`source_artifact_id`), and `verification_status`. Guarded by BEFORE trigger `trg_ca_event_verification_guard`.
3. **Adjustment Factor Ledger (`corporate_action_adjustment_factors`)**: Stores numeric price and volume factors. Guarded by BEFORE INSERT trigger `trg_ca_factor_ingest_guard` and append-only trigger `trg_ca_factor_guard`.
4. **Security Definer Stored Procedure (`ca.apply_verified_corporate_action`)**: Owned by `ca_security_admin`. Validates that the event has `VERIFIED_EXCHANGE_PRIMARY`, the artifact is `PRIMARY_VERIFIED`, and the factor matches before updating `ohlcv_daily.adjusted_close`.
5. **Database Role Privileges**: `halal_user` (superuser), `ca_security_admin` (non-login procedure owner), and `halal_app_user` (application role).

### 1.2 Discovery of Application-Role Privilege Vulnerability

A critical security vulnerability was discovered during our adversarial audit:

In **Migration 21** ([`backend/migrations/21-p195-runtime-least-privilege-app-user.sql`](file:///Users/fayas/Downloads/ICO-Application/analysis%20application/backend/migrations/21-p195-runtime-least-privilege-app-user.sql#L45-L50)), table permissions were granted as follows:
```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON 
    corporate_action_source_artifacts, 
    corporate_action_events, 
    corporate_action_adjustment_factors 
TO halal_app_user;
```

**The Vulnerability**:
Because `halal_app_user` possessed table INSERT privileges, and because `fn_ca_event_verification_guard()` only checked that `source_url` matched exchange domain patterns and `validation_status = 'PRIMARY_VERIFIED'`, an ordinary application process or compromised endpoint connecting as `halal_app_user` **could insert a forged artifact with `source_url = 'https://www.nseindia.com/mock.pdf'`, label it `PRIMARY_VERIFIED`, insert a corresponding event claiming `VERIFIED_EXCHANGE_PRIMARY`, and un-quarantine historical bars**!

We proved this vulnerability with live adversarial execution:
```sql
-- Executed as halal_app_user before remediation:
INSERT INTO corporate_action_source_artifacts (..., source_url, validation_status) 
VALUES (..., 'https://www.nseindia.com/mock.pdf', 'PRIMARY_VERIFIED') RETURNING id; -- SUCCEEDED (id=104)

INSERT INTO corporate_action_events (..., verification_status, source_artifact_id) 
VALUES (..., 'VERIFIED_EXCHANGE_PRIMARY', 104); -- SUCCEEDED
```

### 1.3 Metadata Validation vs. True Cryptographic Authenticity

Our audit confirms that:
- **Checking a URL pattern (`https://www.nseindia.com/...`) or a boolean status flag does NOT prove source authenticity**.
- A local SHA-256 hash merely confirms that the bytes stored on disk have not mutated; it does not prove that the National Stock Exchange of India actually authored or published those bytes.
- True cryptographic primary-source authenticity requires:
  1. A digitally signed exchange circular PDF verified against the authorized exchange DSC (Digital Signature Certificate) X.509 root; OR
  2. A cryptographically authenticated machine-to-machine feed with verifiable TLS session provenance, published timestamp, and non-repudiation sequence numbers; OR
  3. Official MCA/NCLT statutory filings with authenticated corporate seal verification.
- **Current Repository State**: No digital signatures or DSC certificates exist for the archived JSON files. All scraped payloads are local historical text archives.
- **Therefore, no event can legitimately claim `VERIFIED_EXCHANGE_PRIMARY`**. All 58 unauthenticated events must strictly remain `ARCHIVE_UNAUTHENTICATED`.

### 1.4 Hardening via Migration 23

To permanently eliminate this vulnerability, **Migration 23** ([`backend/migrations/23-p1913-independent-evidence-authentication-hardening.sql`](file:///Users/fayas/Downloads/ICO-Application/analysis%20application/backend/migrations/23-p1913-independent-evidence-authentication-hardening.sql)) was implemented and applied:

1. **Trigger-Level Privilege Guard on Artifacts**:
   ```sql
   CREATE OR REPLACE FUNCTION ca_artifact_guard() RETURNS TRIGGER AS $$
   BEGIN
       IF TG_OP IN ('UPDATE', 'DELETE') THEN
           RAISE EXCEPTION 'corporate_action_source_artifacts is append-only: UPDATE and DELETE are strictly prohibited (fail-closed)';
       END IF;
       IF TG_OP = 'INSERT' AND NEW.validation_status = 'PRIMARY_VERIFIED' AND CURRENT_USER = 'halal_app_user' THEN
           RAISE EXCEPTION 'Privilege boundary violation: application role halal_app_user cannot manufacture PRIMARY_VERIFIED artifacts';
       END IF;
       RETURN NEW;
   END;
   $$ LANGUAGE plpgsql;
   ```
2. **Trigger-Level Privilege Guard on Events**:
   ```sql
   -- Inside fn_ca_event_verification_guard:
   IF NEW.verification_status = 'VERIFIED_EXCHANGE_PRIMARY' OR NEW.coverage_status = 'HARVESTED_EXCHANGE_PRIMARY' THEN
       IF CURRENT_USER = 'halal_app_user' THEN
           RAISE EXCEPTION 'Event verification rejected: application role halal_app_user cannot assign VERIFIED_EXCHANGE_PRIMARY (privilege boundary violation)';
       END IF;
       ...
   END IF;
   ```
3. **Trigger-Level Privilege Guard on Factors**:
   ```sql
   -- Inside ca_factor_ingest_guard:
   IF (NEW.is_verified = TRUE OR NEW.price_factor_applicable = TRUE) AND CURRENT_USER = 'halal_app_user' THEN
       RAISE EXCEPTION 'Ingestion rejected: application role halal_app_user cannot insert verified adjustment factors (privilege boundary violation)';
   END IF;
   ```

Adversarial testing confirms that `halal_app_user` is now completely blocked from manufacturing verified claims.

### 3.2 Look-Ahead Bias and Timestamp Semantics

The database constraint `ck_ohlcv_daily_session_stamp` requires all daily bars to be stamped with:
$$\text{Timestamp (UTC)} = \mathbf{03:45:00\text{ UTC}}$$
$$\text{Timestamp (IST)} = 03:45:00 + 05:30 = \mathbf{09:15:00\text{ IST}}$$

**Forensic Clarification on Session Open Stamping**:
1. `03:45:00 UTC` marks the **Session Open** (the opening bell at 09:15 IST in Mumbai).
2. The daily bar contains the entire session's summary: `open`, `high`, `low`, `close`, and `volume`.
3. **Physical Availability**: `close`, `high`, `low`, and `volume` are physically formed and finalized **only at or after 15:30:00 IST (10:00:00 UTC)**.
4. **Anti-Leakage Execution Invariant**:
   - The timestamp label `03:45:00 UTC` is an identifying **session label**, NOT a publication timestamp.
   - Any trading strategy or backtest executing at market open (09:15 IST / 03:45 UTC) **must evaluate signals using data strictly through Day $D-1$**.
   - If a signal is evaluated on Day $D$'s EOD bar, simulated trade execution **must occur on Day $D+1$ Open** (or at Day $D$ Close at 15:30 IST).
