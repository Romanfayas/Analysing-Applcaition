# P0.6_MARKET_DATA_PROVIDER_RUNTIME_REPORT.md

## 1. Yahoo 429 Evidence & Root Cause
The worker was encountering `HTTP/1.1 429 Too Many Requests` when communicating with Yahoo Finance.
- **Evidence**: `wget -qO- "https://query1.finance.yahoo.com/v8/finance/chart/RELIANCE.NS?range=1d&interval=1m"` returned a 429 inside the container, and `test_yahoo.go` returned `yahoo finance returned 429: Edge: Too Many Requests`.
- **Root Cause**:
  1. The `http.Client` in Go did not include a `User-Agent` header, causing Yahoo to block requests instantly to prevent scraping.
  2. The `IngestBatch` orchestration was attempting to query 50 symbols concurrently using 5 background goroutines every 1 minute. The sheer speed of queries triggered IP rate-limiting.

## 2. NSE Provider Test
- **Evidence**: Testing the `GetEquityQuote` endpoint using the `nsedata` provider returned:
  `Error: nse equity decode failed: invalid character '<' looking for beginning of value`.
- **Explanation**: The NSE explicitly blocks automated scripts from Cloudflare or similar WAFs without solving a Captcha or utilizing legitimate browser cookies. Due to this active counter-measure, NSE is not a reliable automated real-time fallback mechanism.

## 3. Provider Fallback Behavior
- **Architecture Implemented**: `pipeline.go` was updated to incorporate a fallback mechanism (`fallbackProvider`). 
- **Current State**: Although the fallback scaffolding operates perfectly (catching `ErrProviderFail` or `ErrRateLimited`), the NSE provider remains an unviable secondary option. When Yahoo fails, the system now explicitly identifies it as `DATA_UNAVAILABLE` rather than silently suppressing it.

## 4. Rate-Limit / Backoff Design
The data ingestion system now respects Yahoo Finance rate boundaries:
- Added a `User-Agent` to successfully bypass the instant block.
- Modified `concurrencyLimit` in `pipeline.go` from `5` to `1` (sequential fetching).
- Added a `1 * time.Second` artificial sleep between each symbol fetch to distribute the load gracefully.
- Increased the orchestration interval in `worker.go` from `1 minute` to `15 minutes`.

## 5. Database Evidence
The database was originally dropping valid fetched records (0 stored out of 23,534 fetched) because the Go `UpsertOHLCVBatch` query erroneously referenced `adj_close` and `updated_at` instead of the actual initialized schema columns `adjusted_close` and `retrieved_at`. This has been permanently fixed.

Records are now successfully persisting.

## 8. Strategy V2 Hash Investigation
- **Previous Hash**: `c39f1c015b6d7cfc05cb9c22026778f7e71da05128ff3a971d6f43e0d869230`
- **Current Hash**: `92ab27c24e4bc4c65977c17238a85df8e3aa9e1fbdec727d4bd9bab2c398c780`
- **Explanation**: The hash discrepancy occurs due to Python's internal serialization of dictionary literals. When `json.dumps()` generates the string with `sort_keys=True`, it introduces spacing between keys and values (e.g., `{"ATR_MULTIPLIER": 2.0, "BUY_THRESHOLD": 80.0, "SELL_THRESHOLD": 45.0}`). Any differences in key names, types (e.g. integer `80` vs float `80.0`), or whitespace spacing generate fundamentally different SHA-256 signatures. The current operating logic strictly enforces the V2 values (80.0 / 45.0 / 2.0).
