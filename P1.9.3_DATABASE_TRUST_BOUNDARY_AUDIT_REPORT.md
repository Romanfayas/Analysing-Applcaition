## 1. Executive Summary & Verdict Matrix

In Phase P1.9.2, an adjusted-close quarantine guard was established to protect historical quarantined `NULL` bars from being overwritten by unverified vendor adjusted closes. However, an architectural trust-boundary vulnerability remained: **the database trigger and conflict logic treated the source string (`source IN ('NSE_CORPORATE_ACTION', 'PRIMARY_EXCHANGE')`) as evidence of authorization**. An attacker or faulty ingestion scraper supplying `source = 'NSE_CORPORATE_ACTION'` alongside a fabricated adjusted close could bypass quarantine without providing relational proof of a verified primary exchange corporate action disclosure.

In Phase P1.9.3, this trust-boundary defect was systematically analyzed, reproduced, and eliminated via **Migration 19** (`ca.apply_verified_corporate_action()` and hardened `fn_ohlcv_daily_quarantine_guard()`), Go ingestion hardening, and database permission boundaries.

## 2. Forensic Analysis of P1.9.2 Trust Boundary Defect

### 2.1 The Vulnerability
In P1.9.2, `backend/migrations/18-p192-adjusted-close-quarantine-guard.sql` evaluated incoming rows using literal string matching:
```sql
-- VULNERABLE P1.9.2 LOGIC:
IF OLD.adjusted_close IS NULL THEN
    IF NEW.adjusted_close IS NOT NULL THEN
        IF NEW.source NOT IN ('NSE_CORPORATE_ACTION', 'PRIMARY_EXCHANGE') THEN
            NEW.adjusted_close := NULL;
        END IF;
    END IF;
    RETURN NEW;
END IF;
```
And `repository.go` in `UpsertOHLCVBatchWithStats` allowed:
```go
// VULNERABLE P1.9.2 REPOSITORY LOGIC:
if r.Source == "NSE_CORPORATE_ACTION" || r.Source == "PRIMARY_EXCHANGE" {
    adj = *r.AdjClose
}
```
**Bypass Vector Demonstrated:**
Executing:
```sql
UPDATE ohlcv_daily 
SET adjusted_close = 1200.0, source = 'NSE_CORPORATE_ACTION' 
WHERE symbol_id = (SELECT id FROM symbols WHERE symbol = 'HCLTECH') 
  AND timestamp::date = '2026-10-06';
```
In P1.9.2, this SQL command **succeeded** because `NEW.source = 'NSE_CORPORATE_ACTION'` satisfied the trigger condition, even though no verified corporate action event existed for HCLTECH.

### 2.2 The P1.9.3 Multi-Layered Remediation
To resolve this defect, defense-in-depth was established across four tiers:

1. **Tier 1 (Application Ingestion Layer):**
   In `backend/internal/database/repository.go`, `UpsertOHLCVBatchWithStats` no longer treats any source string in `r.Source` as proof of authorization:
   ```go
   var adj interface{}
   if r.AdjClose != nil && *r.AdjClose > 0 {
       if *r.AdjClose == r.Close {
           adj = *r.AdjClose
       } else {
           // Unverified vendor corporate action adjustment: fail-closed quarantine to NULL.
           // Ordinary ingestion cannot claim trusted corporate action provenance.
           adj = nil
       }
   }
   ```
2. **Tier 2 (Application SQL Conflict Boundary):**
   The `ON CONFLICT (symbol_id, timestamp) DO UPDATE` query clause explicitly rejects excluded adjustments and excluded sources:
   ```sql
   adjusted_close = CASE 
       WHEN ohlcv_daily.adjusted_close IS NULL THEN NULL 
       WHEN ohlcv_daily.source IN ('NSE_CORPORATE_ACTION', 'PRIMARY_EXCHANGE') THEN ohlcv_daily.adjusted_close
       WHEN ohlcv_daily.adjusted_close = ohlcv_daily.close THEN EXCLUDED.close
       ELSE ohlcv_daily.adjusted_close
   END,
   source = CASE
       WHEN ohlcv_daily.source IN ('NSE_CORPORATE_ACTION', 'PRIMARY_EXCHANGE') THEN ohlcv_daily.source
       WHEN EXCLUDED.source IN ('NSE_CORPORATE_ACTION', 'PRIMARY_EXCHANGE') THEN ohlcv_daily.source
       ELSE EXCLUDED.source
   END
   ```
3. **Tier 3 (Database Relational Proof Trigger):**
   In `fn_ohlcv_daily_quarantine_guard()`, an adjustment or trusted source is accepted **only if supported by relational proof**:
   ```sql
   SELECT true, ca.total_return_factor
   INTO v_has_verified_ca, v_active_factor
   FROM corporate_action_adjustment_factors ca
   JOIN corporate_action_events ev ON ev.event_id = ca.event_id 
                                  AND ev.symbol_id = ca.symbol_id
                                  AND ev.verification_status = 'VERIFIED_EXCHANGE_PRIMARY'
   WHERE ca.symbol_id = NEW.symbol_id
     AND ca.is_verified = TRUE
     AND ca.price_factor_applicable = TRUE
     AND ca.dispute_status = 'UNDISPUTED'
     AND NEW.timestamp::date < ca.ex_date
     AND NEW.timestamp::date >= '2026-10-05'
   ORDER BY ca.revision_number DESC
   LIMIT 1;
   ```
   If `v_has_verified_ca` is false or `ABS(NEW.adjusted_close - ROUND(NEW.close * v_active_factor, 4)) > 0.0005`, the trigger forces `NEW.adjusted_close := NULL` (or `OLD.close`) and `NEW.source := OLD.source` (or `'yahoo_finance'`).
4. **Tier 4 (Authorized Procedure Boundary):**
   The sole path for applying verified adjustments is `ca.apply_verified_corporate_action()`, which:
   - Validates that the event exists and has `verification_status = 'VERIFIED_EXCHANGE_PRIMARY'`.
   - Validates that the supplied factor matches the undisputed verified factor in `corporate_action_adjustment_factors`.
   - Is declared `SECURITY DEFINER` with fixed `search_path = public, ca, pg_temp`.
